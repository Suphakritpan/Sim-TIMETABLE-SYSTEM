## 2. ข้อตกลงเพื่อให้เชื่อมกันได้ (ห้ามละเมิด)

### 2.1 API Contract
1. `docs/API-CONTRACT.md` เป็นสัญญาเดียว Backend ต้องตอบ shape ตามนั้นทุกฟิลด์ ส่วน Frontend จะเขียนรับตามนั้นเท่านั้น
2. **สถานะปัจจุบัน: ยังต้องกระทบยอด** — endpoint ใน template (`/api/jobs`, `/api/jobs/{id}/events` ฯลฯ) เป็นของชั่วคราวที่ F1 จะลบ Frontend ยึด **ตารางหัวข้อ 6 ของ `docs/SPEC.md` ฝั่ง Backend** ให้เพื่อน **ส่งสำเนาตารางนั้น (หรือ `openapi.json` จาก `app.openapi()`) ภายในชั่วโมงแรก** แพนจะเทียบแล้วแก้ contract โดยยึดของ Backend เว้นแต่ขัดกับโจทย์ แล้วแช่แข็ง (ดู 2.2) · **ไม่มีล็อกอิน:** endpoint ที่หน้าเว็บเรียกต้องเป็นสาธารณะ (template ตอนนี้บังคับ admin/staff + cookie ใน `/api/jobs*`) และ production ต้องไม่มี `dev-login`
3. ห้ามเปลี่ยน shape เงียบ ๆ ทุกการเปลี่ยนต้อง: แก้ `API-CONTRACT.md` → ลง Changelog (ระบุ breaking หรือไม่) → แจ้งแพนก่อน merge
4. ฟิลด์ที่เพิ่มได้โดยไม่ breaking: เพิ่มฟิลด์ใหม่ (Frontend ต้องเพิกเฉยฟิลด์ที่ไม่รู้จัก) · ที่ breaking: เปลี่ยนชื่อ/ชนิด/ลบฟิลด์ เปลี่ยนความหมาย สถานะ หรือรหัส error

### 2.2 ช่วงแช่แข็ง contract
- เป้า: แช่แข็ง contract ภายใน **ชั่วโมงที่ 2** ของวัน หลังจากนั้นเปลี่ยนได้เฉพาะแก้บั๊กของ contract ที่ทำให้เชื่อมไม่ได้ และต้องแจ้งทันที
- ที่ต้องแช่แข็งให้ได้ก่อนเขียนจริง: ชื่อ/ที่อยู่ endpoint, รูปแบบ error, สถานะ job, วิธีรับความคืบหน้า (SSE หรือ polling), รูปแบบ `placements`, `check`, `summary`

### 2.3 Fixtures (ตัวเชื่อม)
- เพื่อนส่ง **ตัวอย่าง response จริง** อย่างน้อย: import ถูก, import ผิด (หลายจุด), schedule completed, completed_partial/infeasible, cancelled, evaluation, request interpreted → วางที่ `packages/shared/fixtures/` (แพนใช้สร้าง mock)
- ตัวอย่างต้องมาจากข้อมูลชุดทดลองจริง ไม่ใช่เดาเอง และต้องผ่าน schema เดียวกับ API จริง

### 2.4 พฤติกรรมที่ Frontend พึ่งพา (ต้องเป็นจริง)
| เรื่อง | ข้อตกลง |
|---|---|
| ข้อมูลผิด ≠ API พัง | ไฟล์เปิดได้แต่ข้อมูลผิด → ตอบสำเร็จพร้อม `issues[]` ไม่ใช่ error 4xx/5xx |
| ผลตรวจ | ส่งครบ: จัดครบ X/Y, ครู/ห้อง/กลุ่มชนกี่จุด, ผิดกฎอื่น, คะแนนโทษ, เวลา (วินาที), คำอธิบายสั้น ๆ |
| จัดไม่ได้ | ต้องมีสถานะและ **เหตุผล** ห้ามค้าง |
| Seed | ส่ง `seed` ที่ใช้จริงกลับเสมอ; seed+ข้อมูลเดิม = ผลเดิมทุกครั้ง (ระวัง solver หลาย thread) |
| ยกเลิก | idempotent; หลังยกเลิกต้องจัดใหม่ได้ทันที |
| Progress | ถ้าวัดไม่ได้ ส่ง `null` + `stage` (ห้ามเดาตัวเลข) |
| Excel ส่งออก | แผ่น `ตารางสอน`, หัวคอลัมน์ 6 ช่อง `รหัสรายการสอน · ประเภท · วัน · คาบเริ่ม · จำนวนคาบ · รหัสห้อง` ตรงทุกตัวอักษร (กรรมการตรวจด้วยโปรแกรม) เทียบกับ `4_ตัวอย่างไฟล์ตารางสอนที่ต้องส่งออก.xlsx` |
| คำขอพิเศษ | LLM ล่ม ต้องไม่ทำให้ทั้งหน้าพัง ให้คืนรายการที่ตีความไม่ได้เพื่อให้กรอกเองผ่านฟอร์ม |
| ข้อมูลชุดใหม่ | ห้ามฝังรหัสครู/ห้อง/กลุ่ม/จำนวนคาบ/ตารางเวลาของไฟล์ตัวอย่างในโค้ด |
| ชุดใหญ่ ~600 รายการ | ต้องไม่ค้าง ต้องยกเลิกได้ภายในประมาณ 1 วินาที (เป้าของเพื่อน ยังไม่ได้วัด) |

### 2.5 โครงสร้างพื้นฐาน
- **จุดที่ต้องตัดสินก่อน: Vercel หรือ VPS ทั้งหมด** (ดู §7.5) ถ้าใช้ Vercel + Backend ข้ามโดเมน ต้อง HTTPS+โดเมนจริง, เปิด CORS (template ยังไม่ได้ตั้งใน `main.py`), และทดสอบ SSE ผ่าน Vercel ถ้าใช้ VPS ทั้งหมด (Caddy เสิร์ฟ build ของ `apps/web` ที่ `/` และ proxy `/api`) จะเป็น origin เดียว ไม่มีปัญหา CORS/cookie/SSE ข้ามโดเมน
- CORS: อนุญาตเฉพาะโดเมน Vercel จริง (รวม SSE ถ้าใช้) · ตัวแปรกำหนดผ่าน env `ALLOWED_ORIGINS`
- SSE ผ่าน reverse proxy: ปิด buffering, ตั้ง read timeout ยาว
- Secret (LLM key, DB password) อยู่ใน env ฝั่ง Backend เท่านั้น ห้าม commit และห้ามอยู่ใน `VITE_*`
- ให้มี `apps/api/README.md` บอกวิธีรันในเครื่อง (โจทย์แนะนำ และผู้ตรวจ clone ไปรันเองได้)

### 2.6 วิธีทำงานร่วมกัน
- แต่ละคนแก้เฉพาะโฟลเดอร์ของตน (`apps/web` = แพน, `apps/api` = เพื่อน); `docs/API-CONTRACT.md` และ `packages/shared/**` แก้ร่วมกันตามข้อ 2.1
- `proposition data/**` ห้ามแก้
- commit เล็ก ๆ พร้อมข้อความชัดเจน; ห้ามดัน `.env` หรือ key; ห้าม `push --force` ลง `main`
- เจออะไรที่เอกสารไม่ตอบ ให้ **ถามแล้วบันทึกคำตอบลงเอกสาร** ไม่ตัดสินเงียบ ๆ

## 3. สิ่งที่ฝั่งแพนจะทำ

1. สร้าง `services/` (ตัวสลับ `VITE_DATA_MODE`) + `mocks/` + `schemas/` + fixtures จากไฟล์ชุดทดลอง เพื่อทำ 6 หน้าได้โดยไม่รอ Backend
2. ทำ 6 หน้าแบบพอใช้ก่อน และ **deploy Vercel ให้ได้ตั้งแต่ต้น** แล้วค่อยปรับให้ดีทีละหน้า
3. จัดการ loading / error / empty / success ทุกหน้า และรองรับมือถือ
4. เปลี่ยน mock เป็น API จริงทีละ service เมื่อ endpoint พร้อม ตรวจ shape ด้วย schema
5. ทำไฟล์แม่แบบ/ตัวอย่าง 3 ขนาด (เล็ก/กลาง/ใหญ่) ร่วมกับเพื่อนเรื่องกติกาข้อมูล
6. เตรียมคู่มือ 1 หน้า (เปิดเว็บแล้วกดอะไรตามลำดับ) และข้อมูลส่งงาน (ลิงก์เว็บ ลิงก์ซอร์สโค้ด)
7. แจ้งเพื่อนทันทีเมื่อ response จริงไม่ตรง contract พร้อมตัวอย่าง request/response ที่ผิด

## 7. ข้อควรระวังเพิ่มเติม (เพิ่มภายหลังการทบทวนว่ายังขาดอะไร)

**7.1 กับดักในข้อมูล/โจทย์**
- **ชื่อครูซ้ำบางส่วน:** ในไฟล์มีชื่อต้นหรือนามสกุลซ้ำ (เช่น ประภาพร มูลเมือง กับ ประภาพร พลอยงาม, ศิริพร สองคน, "ภูมิใจ"/"สุขสวัสดิ์"/"มูลเมือง" หลายคน) ตอนจับคู่ชื่อครูในคำขอพิเศษต้องเทียบ **ชื่อ-นามสกุลเต็ม** ห้ามจับแค่ชื่อต้น และถ้าไม่พบครูในข้อมูล → ประเภท `none` (โจทย์ระบุไว้)
- **คำขอที่เป็นจริงอยู่แล้ว:** เช่น "งดจัดคาบช่วงพักกลางวัน" → `none` ไม่ใช่ข้อบังคับใหม่
- **`ห้องที่ใช้เรียนปฏิบัติ` คือประเภทห้อง** ไม่ใช่รหัสห้อง; ทฤษฎีต้องอยู่ห้องประเภทห้องบรรยาย
- **เรียนรวมหลายกลุ่ม:** ทุกกลุ่มต้องว่างพร้อมกัน และความจุห้อง ≥ ผลรวมนักเรียน (ห้อง 90 ที่นั่ง `AUD-01` มีไว้รองรับกรณีนี้)
- **ปฏิบัติหลายคาบต้องติดกัน** และห้ามข้ามพักเที่ยง (คาบ 4→5 ห้าม) ห้ามทับวันพุธคาบ 7–8
- **ข้อมูลที่ไม่เคยเห็น:** ห้ามสมมติว่ามี 5 วัน/8 คาบ/ชื่อประเภทห้องชุดเดิม ควรอ่านจากข้อมูลหรือค่ากำหนดตัวเดียว
- **ผลลัพธ์ "ไม่ผิดกฎ" ≠ ดีที่สุด:** คะแนนโทษยิ่งน้อยยิ่งดี (ก–ง ดู contract §1.2) ส่วนข้อ จ น้ำหนักทีมกำหนดเอง ต้องบันทึกไว้อธิบายตอนนำเสนอ

**7.2 เรื่องที่โจทย์ให้คะแนนแต่เอกสารอื่นยังไม่ได้ชี้**
- หน้า 5 ชื่อ "ผลการใช้ AI" และโจทย์เขียน "วิธี AI ของทีม" → **ต้องมีส่วนที่เป็น AI จริงและอธิบายได้ว่าใช้ตรงไหน ตั้งค่าอะไร** (เช่น local search/metaheuristic/ตัวแก้ constraint หรือ LLM) เพื่อนต้องเลือกและบอกแพนเพื่อเขียนคำอธิบายบนหน้า และเป็นหัวข้อนำเสนอ 10 นาที (15 คะแนน)
- ผลต้อง **ดีกว่าวิธีพื้นฐานเป็นตัวเลขจริง** และกดซ้ำด้วย seed เดิมได้ผลเดิม

**7.3 ค่าเริ่มต้นตามแนวปฏิบัติที่ดี (DEFAULT — ใช้ตามนี้เว้นแต่มีคนคัดค้านและบันทึกเหตุผลลงเอกสาร)**

| เรื่อง | ค่าเริ่มต้น | เหตุผล |
|---|---|---|
| สิทธิ์ repo | **เพื่อนได้รับสิทธิ์แล้ว** (ผู้ใช้ยืนยัน) ให้ตรวจว่า push/สร้าง PR ได้จริง | พร้อมทำงาน |
| Git / branch | `main` ป้องกันไว้ ห้าม `push --force`; ทำงานบน branch สั้นต่อฟีเจอร์ (`web/…`, `api/…`) แล้วเปิด PR เข้า `main` อย่างน้อยอีกคนดูก่อน merge (วันนี้เวลาน้อย: ให้ดูเฉพาะ PR ที่แตะ contract/fixtures/ไฟล์ส่งออก); merge แบบ squash | ลดการชนกัน ย้อนกลับง่าย Vercel สร้าง preview ให้ทุก PR |
| Vercel | Production deploy จาก `main`; Root Directory = `apps/web`; ตั้ง env ใน Vercel (ไม่ commit) | ตรงที่ตกลง |
| ใครแตะอะไร | `apps/web` = แพน, `apps/api` = เพื่อน; `docs/API-CONTRACT.md` + `packages/shared/**` แก้ผ่าน PR ที่ให้อีกฝ่ายอนุมัติ | กันเปลี่ยน contract เงียบ ๆ |
| Commit | ข้อความชัด ขนาดเล็ก; ห้าม commit `.env`, key, ไฟล์ข้อมูลจริง; ตั้ง `.gitignore` และตรวจ secret ก่อน push | ความปลอดภัย (repo เปิดสาธารณะ) |
| LLM | **ใช้ของฟรีไปก่อน** (ผู้ใช้ตัดสิน): key เป็น env ฝั่ง Backend เท่านั้น; เพราะของฟรีมักจำกัดอัตราเรียก/ล่มได้ จึงต้อง (1) แคชผลตีความตามข้อความคำขอ (2) จำกัดจำนวนเรียกพร้อมกัน + timeout สั้น + retry ไม่กี่ครั้ง (3) ตีความด้วยกฎ/ฟอร์มเมื่อ LLM ใช้ไม่ได้ (4) **ตีความไว้ล่วงหน้า** กับไฟล์ตัวอย่างและเก็บผล เพื่อไม่พึ่ง LLM สดตอนกรรมการลอง (ข้อมูลชุดใหม่ของกรรมการยังต้องเรียกสด จึงต้องมี fallback) ทดสอบความถูกต้องของการตีความกับคำขอใน 2 ไฟล์ตัวอย่างก่อนพึ่งพา | ไม่ล้มกลางวันตรวจ ไม่รั่ว key ไม่เสียเงิน |
| VPS / การเข้าถึงเครื่อง | **VPS รัน Docker อยู่แล้ว** (ผู้ใช้ยืนยัน) → Backend, Worker และ PostgreSQL รันด้วย docker compose + volume ถาวร (ฐานข้อมูล, `FILES_DIR`); เพื่อนเป็นคน deploy เข้าเครื่องด้วย SSH key ไม่ใช่รหัสผ่าน; **ห้ามส่ง SSH/รหัสผ่าน/key ในแชตหรือ repo**; เปิดเฉพาะพอร์ต 80/443 และ SSH; ตั้ง `restart: unless-stopped` และตรวจว่า stack กลับมาเองหลังรีบูต | ลดความเสี่ยง ทนรีสตาร์ท |
| โดเมน + HTTPS | ใช้โดเมน (หรือ subdomain) ชี้ VPS ให้ Caddy ออกใบรับรองอัตโนมัติ; ตั้งค่า `ALLOWED_ORIGINS` เป็นโดเมน Vercel จริง | เว็บ HTTPS เรียก API ได้ |
| ไฟล์ตัวอย่างขนาดใหญ่ | เพื่อนเขียนตัวสร้างข้อมูลสุ่มแบบ **กำหนด seed** (`scripts/make_samples.py`) ให้มั่นใจว่าจัดได้จริง แพนวางผลใน `apps/web/public/samples/` และ commit พร้อม seed ที่ใช้ | ทำซ้ำได้ ตรวจสอบได้ |
| Dev ในเครื่อง | Backend `:8000`, Frontend Vite ตามพอร์ตมาตรฐาน; `ALLOWED_ORIGINS` โหมดพัฒนารวม `http://localhost:5173` เฉพาะ dev (ห้ามเปิด `*` บน production) | ทดสอบรวมได้ |
| ตรวจรับ | ก่อนส่ง: CI/สคริปต์รัน lint + test + build ทั้งสองฝั่งให้ผ่าน; ซ้อมแบบกรรมการ (ไฟล์ใหม่ ชุดใหญ่ ยกเลิก seed ซ้ำ ดาวน์โหลด Excel/PDF มือถือ) เริ่ม **15.00 น.** ทิ้งเวลา 1 ชม. แก้ ก่อนส่ง 16.30 น. | ลดความเสี่ยงวันจริง |
| Release freeze | **16.00 น. หยุดฟีเจอร์ใหม่** เหลือแก้บั๊กวิกฤตเท่านั้น; ก่อนส่งติด tag `submission` ใน git และจดลิงก์เว็บ/ซอร์สโค้ด | หลัง 16.30 แก้ไม่ได้ |
| Fallback วันตรวจ | เตรียมคู่มือรันในเครื่อง (`docker compose up`) และบันทึกวิดีโอ/ภาพหน้าจอผลเมื่อ VPS ล่ม | โจทย์แนะนำ |

**7.4 จังหวะการทำงานร่วมกัน**
- เช็คพอยต์สั้น ๆ ทุก 2 ชั่วโมง: เสร็จอะไร / ติดอะไร / contract เปลี่ยนไหม
- ติดเกิน 30 นาที ให้แจ้งทันที เพื่อตัดขอบเขตให้ทัน (ตัดความสวย/PDF/คำอธิบายก่อน ห้ามตัดความถูกต้องของกฎ, seed, รูปแบบ Excel)
- ข้อตกลงใหม่ที่เกิดระหว่างคุยกัน ให้จดลงเอกสารที่เกี่ยวข้องทันที (ไม่เก็บไว้ในแชต)

**7.5 สถานะเรื่องที่เคยเปิดอยู่ (อัปเดต)**
| เรื่อง | สถานะ |
|---|---|
| VPS ใช้ Docker | ตัดสินแล้ว — docker compose |
| LLM | ตัดสินแล้ว — ใช้ของฟรีไปก่อน (ต้องมี fallback + แคช ตาม §7.3) |
| สิทธิ์ repo ของเพื่อน | ได้รับแล้ว |
| **โดเมนจริงของ Backend (HTTPS)** | **ยังไม่ได้คำตอบ — ยังบล็อกการเชื่อม Vercel → Backend** ต้องได้โดเมน/subdomain ที่ชี้ VPS |
| รายการ endpoint จริงของ template | ยังรอเพื่อนส่ง (ดู §2.1 ข้อ 2) |

**7.6 ข้อมูลใหม่จากเพื่อน (บันทึกล่าสุด)**
- สเปกฝั่ง Backend วางแผนรัน **ทุกส่วน (web, API, worker, database) บน VPS ด้วย docker compose — ไม่ได้ใช้ Vercel** ขัดกับที่แพนวางแผนไว้ (Vercel Root = `apps/web`) ต้องตัดสินใจ (ดูตารางด้านล่าง)
- ถ้าแยกเว็บไว้ `*.vercel.app` แต่ API อยู่อีกโดเมน: cookie `SameSite=Lax` ของ template จะไม่ถูกส่งข้ามโดเมน (ไม่กระทบถ้าไม่มีล็อกอิน), CORS ต้องเพิ่ม, SSE ผ่าน rewrite ของ Vercel อาจถูกตัด ต้องทดสอบจริง
- ยังไม่มีโดเมน (Q1 ในสเปกเพื่อน): ต้องเป็น (sub)domain ที่ A record ชี้ IP ของ VPS เช่น `api.<โดเมนของผู้ใช้>` ผมตั้งชื่อเองไม่ได้ ถ้าจะไม่ซื้อโดเมน ทางเลือก (ผมไม่ได้ทดสอบ): hostname ฟรีที่แปลงจาก IP เช่น `<ip>.sslip.io` หรือ DuckDNS ซึ่ง Caddy ขอใบรับรองได้ — เพื่อนต้องลองจริง

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| **A. VPS ทั้งหมด (เพื่อนแนะนำ และผมเห็นด้วย)** | origin เดียว ตัด CORS/cookie/SSE ข้ามโดเมน; deploy ที่เดียว; ตรงสเปก Backend | VPS ล่ม = ทั้งเว็บล่ม; ไม่มี preview ต่อ PR |
| B. Vercel (web) + VPS (API) | web ขึ้นเร็ว มี preview; web ไม่ล่มตาม VPS | ต้องมีโดเมน HTTPS, CORS, ทดสอบ SSE ข้ามโดเมน, ต้องแก้สเปก |

**ผู้ใช้เลือก B (Vercel + VPS) แล้ว** → แพนคงแผน Vercel; เพื่อนต้องทำ CORS, ทดสอบ SSE ข้ามโดเมน, โดเมน HTTPS ตาม [DEPLOYMENT.md](DEPLOYMENT.md) และสเปกฝั่ง Backend ต้องแก้ให้สอดคล้อง (เดิมระบุรันเว็บบน VPS) · **คำขอรายละเอียดที่ให้เพื่อนโยนเข้า AI: [REQUEST-TO-BACKEND.md](REQUEST-TO-BACKEND.md)**
