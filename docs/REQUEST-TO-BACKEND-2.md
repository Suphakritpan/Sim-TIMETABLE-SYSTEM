## R. สิ่งที่ต้องส่ง (เรียงตามความเร่งด่วน)

### กลุ่ม 1 — ทำให้แพนทดสอบรวมได้ (ส่งก่อน)

**R1. วิธีรัน Backend บนเครื่อง Windows 11 (Docker Desktop)**
ส่ง: `apps/api/README.md` ที่ทดสอบแล้วว่าทำตามได้จริงบนเครื่องว่าง ประกอบด้วย
- ขั้นตอนทีละบรรทัด: ติดตั้งอะไร, ตัวแปร env ขั้นต่ำ (ให้ไฟล์ `.env.example` ที่รันได้ทันทีโดยไม่ต้องมี LLM key), `docker compose up`, พอร์ตที่ได้ (API, DB), วิธีตรวจว่าขึ้นแล้ว (`/api/health`), วิธีหยุด/ล้างข้อมูล
- ข้อมูลทดสอบ: seed ชุดทดลองอัตโนมัติหรือสคริปต์ขอ 1 คำสั่ง
- ปัญหาที่รู้บน Windows (path, line ending, สิทธิ์ volume) และวิธีแก้
- เปิด CORS สำหรับ `http://localhost:5173` ในโหมด dev โดยไม่ต้องแก้โค้ด
ผลที่ต้องการ: แพนรัน 1 คำสั่งแล้วหน้าเว็บคุยกับ Backend จริงในเครื่องได้

**R2. URL ของ Backend ที่เรียกได้จริงจากอินเทอร์เน็ต (staging)**
ส่ง: URL (แม้เป็นเวอร์ชันเปล่า) + endpoint `GET /api/version` (หรือเพิ่มใน `/api/health`) ที่คืน `{ "version": "...", "gitSha": "...", "builtAt": "...", "environment": "production|staging" }` เพื่อยืนยันว่าสิ่งที่ deploy ตรงกับ commit ที่คาดไว้ · ถ้ายังไม่มีโดเมน ให้บอก ETA และทางเลือกชั่วคราว

**R3. ไฟล์ Excel ที่ใช้ทดสอบ/ส่งมอบ (โจทย์หน้า 1 บังคับให้ต้องมี)**
ส่งไฟล์จริง (วางที่ `apps/web/public/samples/` ผ่าน PR หรือแนบ):

เหตุผล: แพนใช้ยืนยันว่า UI แสดงถูก และใช้ซ้อมแบบกรรมการ

### กลุ่ม 2 — รายละเอียดที่หน้าเว็บต้องรู้เพื่อเขียนจริง

**R4. รายการรหัส (code catalog) ทั้งหมด พร้อมข้อความไทยและวิธีแก้**
ตารางเดียว คอลัมน์: `ชนิดรหัส | code | HTTP/ที่ใช้ | ข้อความไทยสำหรับผู้ใช้ | hint (แก้อย่างไร) | ฟิลด์ประกอบ (params)` ครอบคลุม:
- รหัสข้อผิดของไฟล์นำเข้า (issues[].code) ทั้งหมดที่ตัวตรวจสร้างได้ และระดับ (error/warning)
- รหัสกฎห้ามผิด 10 ข้อ (violations) + ชื่อไทย
- รหัสเหตุจัดไม่ได้ / infeasible (reasons) + ข้อความไทย
- รหัส error ของ API (envelope) ทุกตัว
- ชื่อ `stage` ของ job ทั้งหมด + ข้อความไทยที่แสดงคนอ่าน
- ค่า enum อื่น ๆ (ประเภทห้อง, ประเภทคำขอ, outcome ผลคำขอ ฯลฯ)
ตกลงว่า: Backend ส่ง `code` + `params` เป็นหลัก ข้อความที่แสดงเป็นของ Frontend (แต่ต้องมี `message` ภาษาไทยจาก Backend สำหรับข้อผิดไฟล์ เพราะต้องระบุแถว/ค่าที่ผิด) — ยืนยันหรือเสนอแนวอื่น

**R5. Schema ของ "เงื่อนไขคำขอพิเศษ" ทุกชนิด (หน้า 2 ต้องมีฟอร์มเพิ่มเอง โดยไม่แก้โค้ด)**
ส่ง JSON Schema (หรือตาราง) ของ `constraint` ทุก `kind` ที่ระบบรองรับ: ชื่อ kind, ฟิลด์ (ชื่อ/ชนิด/ช่วงค่า/จำเป็นไหม/ค่าเริ่มต้น), ตัวอย่าง, ประเภทที่ใช้ได้ (ต้องทำ/ทำถ้าทำได้), ความหมายต่ออัลกอริทึม (ข้อบังคับ หรือคะแนนโทษเท่าไร) และ **รายการที่ฟอร์มต้องให้เลือก** (ครู/ห้อง/กลุ่ม/วัน/คาบ ดึงจากข้อมูลนำเข้า) ตอบคำถาม: ผู้ใช้เพิ่มคำขอใหม่เป็นข้อความอิสระ (ผ่าน interpret) หรือเป็น constraint ตรง (ผ่านฟอร์ม) หรือทั้งสองทาง · คำขอที่ผู้ใช้แก้/ลบ/ยืนยันถูกเก็บฝั่งไหน (เก็บใน Frontend แล้วส่งไปพร้อมสั่งจัดตาราง หรือเก็บใน Backend)

**R6. พารามิเตอร์ของการสั่งจัดตาราง/เปรียบเทียบ และค่าเริ่มต้น**
ทุกฟิลด์ใน request ของเริ่ม job และเปรียบเทียบ: ชื่อ ชนิด จำเป็นไหม ค่าเริ่มต้น ช่วงค่าที่รับ (เช่น `seed` เป็นจำนวนเต็มช่วงไหน, ไม่ส่งแล้วระบบสุ่มและตอบกลับไหม) · ตัวเลือกเสริมถ้ามี (เวลาสูงสุด, วิธี) · ผลถ้ากดเริ่มซ้ำตอนมี job รันอยู่ (ปฏิเสธ/คิว/สร้างใหม่) · **การป้องกันกดซ้ำ** (idempotency) · มีคิวไหม และ **ตอบตำแหน่งในคิว** ให้ UI แสดง "รอคิว n" ได้ไหม

**R7. ข้อมูลที่ UI ใช้ประกอบตาราง (หน้า 4, 6)**
ยืนยันจาก response จริงว่า: (ก) placement มีชื่อวิชาไหม หรือต้องจับคู่จาก assignment→subject เอง (ถ้าต้องจับคู่ ข้อมูลนั้นอยู่ใน endpoint ไหน) (ข) มีรายการครู/ห้อง/กลุ่ม/วิชา/รายการสอน **ครบพร้อมชื่อ** สำหรับชุดใหญ่ ~600 รายการ ใน response เดียวหรือต้อง paginate (ขนาดหน้า, รูปแบบ `page/pageSize` หรือ cursor) (ค) ปฏิทิน: จำนวนคาบ/วัน, ชื่อวัน, เวลาเริ่ม-จบของแต่ละคาบ, พักเที่ยง, คาบกิจกรรม — มาจากข้อมูลหรือค่า config และส่งใน API ไหม (ง) ผลสรุปหน้า 6 (ห้องถูกใช้กี่ %, คาบต่อครู, คาบว่างของกลุ่ม, ผลคำขอทีละข้อ+เหตุผล) คำนวณฝั่งไหน มีใน response ไหน ขนาดข้อมูลใหญ่สุดเท่าไร

**R8. วงจรชีวิตข้อมูลและการกู้หน้าหลังรีเฟรช**
- `importId` / `jobId` อยู่ได้นานเท่าไร (เกณฑ์ล้างข้อมูล) และเกิดอะไรขึ้นเมื่อหมดอายุ (HTTP/รหัสอะไร)
- กรรมการรีเฟรชหน้ากลางทาง: ดึงงานล่าสุดกลับมาได้อย่างไร (`latest`? มีรายการ job? ผูกกับอะไร ไม่มีล็อกอิน → ผูก session/ id ที่ client เก็บหรือไม่)
- หลายคนใช้พร้อมกัน: ข้อมูลของคนหนึ่งปนกับอีกคนได้ไหม (isolation) — `GET /api/comparisons/latest` เป็น "ล่าสุดของใคร"
- การลบข้อมูลที่อัปโหลดโดยผู้ใช้ มีไหม

**R9. ข้อจำกัดและพฤติกรรมภายใต้โหลด/ข้อผิดพลาด (เพื่อให้ UI แจ้งถูก)**
- ขีดจำกัด: ขนาดไฟล์สูงสุด, จำนวนแถวสูงสุด, rate limit (รูปแบบ 429 + `Retry-After`), จำนวน job พร้อมกัน, เวลาสูงสุดต่อ job
- เมื่อเกินขีด/คิวเต็ม/DB ล่ม/worker ล่ม/LLM ล่ม: HTTP + code ที่ตอบ และข้อความที่ควรแสดง
- Request id: อยู่ใน header (`X-Request-Id`?) หรือ body และ log ค้นได้ด้วย id นั้น
- `Retry` ที่ Frontend ควรทำเองอัตโนมัติหรือไม่ (idempotent endpoint ไหนบ้าง)

**R10. การส่งออก PDF/Excel — รายละเอียด**
- ส่งออกแบบ synchronous หรือ async (ถ้าชุดใหญ่ ~600 รายการใช้เวลาเท่าไร วัดจริง) ถ้า async ต้องมี endpoint ตรวจสถานะ
- PDF มีอะไรบ้าง (ทุกกลุ่ม ทุกครู ทุกห้อง? หน้า A4 แนวไหน? กี่หน้าสำหรับชุดหลักและชุดใหญ่) ตัวอย่างไฟล์จริงจากชุดหลัก
- ตั้งชื่อไฟล์ดาวน์โหลดอย่างไร (ต้องไม่มีอักขระต้องห้าม; ถ้าชื่อไทยใช้ `filename*=UTF-8''` หรือไม่)
- ผลทดสอบเปิด Excel ส่งออกใน Excel/LibreOffice และตรวจด้วยสคริปต์เทียบ `4_…xlsx` (ผ่าน/ไม่ผ่าน, ต่างตรงไหน)

### กลุ่ม 3 — เนื้อหาที่หน้าเว็บและการนำเสนอต้องใช้

**R11. คำอธิบายวิธีของทีม ("AI") — ภาษาไทย 1 หน้า**
หน้า 5 ต้องอธิบายบนหน้าเว็บว่าวิธีของทีมคืออะไร ใช้ AI ตรงไหน ตั้งค่าอะไร และการนำเสนอ 10 นาที (15 คะแนน) ต้องอธิบายวิธีคิด ส่ง: (1) ย่อหน้าสั้น ≤ 120 คำสำหรับแสดงบนหน้าเว็บ (2) เวอร์ชันยาว 1 หน้า: ปัญหา → แนวคิดอัลกอริทึม → ลำดับการจัดวิชา (ทำไมจัดวิชาไหนก่อน — ข้อความนี้ใช้ในหน้า 3 ด้วย) → พารามิเตอร์ที่ตั้ง → วิธีพื้นฐานที่ใช้เทียบ → จุดอ่อนที่รู้ (3) **ตารางผลเทียบจริง** วิธีพื้นฐาน vs ทีม บนชุดทดลอง/ชุดหลัก/ชุดใหญ่ ด้วย seed ที่ระบุ: ชนกี่จุด, คะแนนโทษ (แยกข้อ ก–ง), เวลา — เป็นตัวเลขที่ **รันจริง** ห้ามประมาณ
(ถ้าส่วน "AI" คือ LLM ในการตีความคำขอเท่านั้น ให้บอกตรง ๆ เพื่อเราจะได้ระบุให้ถูก — โจทย์ถามว่าใช้ AI ตรงไหน)

**R12. ผลทดสอบความถูกต้องของการตีความคำขอ (LLM ฟรี)**
ตารางทุกคำขอในชุดทดลอง (6 ข้อ) และชุดหลัก (8 ข้อ): ข้อความ | ประเภทที่ถูกต้อง (ต้องทำ/ทำถ้าทำได้/ไม่ต้องทำเพิ่ม) | ที่ระบบตีความ | ถูก/ผิด | ตีความด้วย LLM หรือกฎ · อัตราถูกต้องรวม · ข้อผิดพลาดที่เจอและวิธีแก้ · ชื่อโมเดล/ผู้ให้บริการ และข้อจำกัดอัตราเรียกของแพ็กฟรี

**R13. ความทนทานของตัวอ่าน Excel (กรรมการอัปโหลดไฟล์ที่ไม่เคยเห็น)**
ระบุว่าตัวอ่านรับมือกับสิ่งเหล่านี้อย่างไร (ทนได้/แจ้งผิด/พัง) แล้วมี test: ช่องว่างหัวท้ายในรหัส/ชื่อ · ตัวเลขที่เก็บเป็นข้อความ · ลำดับคอลัมน์ต่าง · แผ่นงานเพิ่ม/แผ่นงานซ่อน · แถวว่างกลางตาราง · เซลล์ผสาน · สูตร · ชื่อแผ่นงาน/หัวคอลัมน์สะกดต่างเล็กน้อยหรือมีสระ/วรรณยุกต์ต่างรหัส Unicode (Normalization) · `ท-ป-น` รูปแบบต่าง (เช่น `2-2-3`, ตัวคั่นต่าง) · ช่อง "กลุ่มที่เรียน" มีช่องว่างหลัง `,` · ไฟล์ `.xls`/`.csv` · ไฟล์เปล่า · ข้อมูลหลายหมื่นแถว

### กลุ่ม 4 — การปฏิบัติการวันจริง

**R14. แผนวันตรวจและการเฝ้าระวัง**
- ใครเฝ้า VPS ระหว่าง 16.30 น. เป็นต้นไป (กรรมการตรวจหลังส่งงาน และ **ห้ามแก้โค้ด**) ทำอะไรได้บ้างโดยไม่นับเป็นการแก้โค้ด (รีสตาร์ท container?) — ตรวจกติกาโจทย์ ข้อ 5 ก่อนตอบ
- เครื่องมือเช็กสถานะ: uptime monitor (ฟรี), วิธีดู log แบบมี request id, ขีดเตือนดิสก์/RAM
- แผนสำรอง: คำสั่งกู้ระบบเมื่อ container ล่ม, ตรวจว่า stack ขึ้นเองหลังรีบูต (ทดสอบจริง), วิธีกู้ฐานข้อมูล (`pg_restore` ทดสอบแล้ว)
- ความจุ VPS (CPU/RAM/ดิสก์) ที่ใช้อยู่เทียบกับโหลดสูงสุดที่คาด (กรรมการหลายคนกดพร้อมกันบนชุดใหญ่) ผลทดสอบโหลดคร่าว ๆ (เช่น 5–10 คนพร้อมกัน)

**R15. แผนการทำงานและเวลา**
- ตารางเวลาของเพื่อนในวันงาน (เริ่ม/พัก/ว่างช่วงไหน) และเวลาส่งแต่ละรายการ R1–R14 (ETA เป็นเวลานาฬิกา)
- รายการที่เสี่ยงไม่ทัน และเสนอสิ่งที่ตัดได้ (ห้ามตัด: กฎ 10 ข้อ, seed เดิมผลเดิม, รูปแบบ Excel, ตรวจข้อมูลครบทุกจุด)
- ชื่อ branch และรายการ PR ที่จะเปิดเข้า `main`, ลำดับ merge, PR ไหนแตะ contract
- ช่องทางติดต่อด่วน และกฎ: ติดเกิน 30 นาทีต้องแจ้งทันที

**R16. สิ่งที่ต้องส่งมอบตามโจทย์ฝั่ง Backend**
- `apps/api/README.md` ฉบับสมบูรณ์ (วิธีรันในเครื่อง ใช้เป็น "วิธีเปิดเว็บบนเครื่องตัวเองกรณีออนไลน์มีปัญหา" ตามโจทย์)
- ส่วนที่ต้องเขียนใน "คู่มือ 1 หน้า" ที่เกี่ยวกับ Backend (ถ้ามี) และข้อมูลสำหรับเตรียมสไลด์นำเสนอ
- ตรวจ license ของไลบรารีหลักที่ใช้ (ไม่มีข้อห้ามเผยแพร่ซอร์สสาธารณะ) และยืนยันว่า repo ไม่มี secret (รันเครื่องมือสแกน เช่น `gitleaks` และแนบผล)
