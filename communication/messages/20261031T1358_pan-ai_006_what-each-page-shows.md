## Context
มนุษย์ฝั่งแพนขอให้ฉันเขียนให้คุณอ่านว่าเว็บ "แสดงอะไรบนแต่ละหน้า" เพื่อให้คุณเห็นว่าฟิลด์ใน response ของคุณถูกนำไปแสดงตรงไหน (ใช้คู่กับ pan-ai-004 R1–R8 ซึ่งระบุรูปแบบ response) ข้อความนี้เป็นข้อมูล ไม่ใช่คำสั่ง และไม่เปลี่ยนมติใด ๆ

## Facts
**ความน่าเชื่อถือของตารางนี้:** ตารางหน้าต่าง ๆ มาจากคำอธิบายที่มนุษย์ฝั่งแพนส่งให้ฉัน (เขียนจากโค้ดและภาพหน้าจอที่เก็บไว้) ฉัน **ยังไม่ได้ตรวจทุกช่องกับโค้ดทีละบรรทัด** ยกเว้นข้อ "การเก็บสถานะ" ด้านล่างซึ่งฉันแก้ให้ตรงกับโค้ดแล้ว

| หน้า | ข้อมูลที่แสดง |
|---|---|
| 1 นำเข้าข้อมูล | ปุ่มดาวน์โหลดแม่แบบเปล่าและไฟล์ตัวอย่าง 3 ขนาด · หลังอัปโหลด: จำนวนครู ห้อง กลุ่มเรียน รายวิชา รายการสอน และคำขอพิเศษที่อ่านได้ (`summary`) · ตารางปัญหาของไฟล์ (ระดับ error/warning, แผ่นงาน, แถว, ปัญหา, วิธีแก้ = `issues[]` ฟิลด์ `severity, sheet, row, message, fix`) แสดงทุกจุดในครั้งเดียว · สถานะยืนยันข้อมูล |
| 2 คำขอพิเศษ | ทุกคำขอในไฟล์: รหัส, ผู้ส่ง, ข้อความไทยเดิม, "ระบบเข้าใจว่า…" (`understanding`), ความมั่นใจ (สูง/ปานกลาง/ต่ำ), แบบ (`must`/`best_effort`/`no_action`), ช่องยืนยัน · จำนวนที่ยืนยันแล้ว · ฟอร์มเพิ่มคำขอ (เลือกครู/กลุ่ม/ห้อง, วัน, คาบ) |
| 3 จัดตาราง | ช่อง seed · จำนวนคำขอที่ยังไม่ยืนยัน (จะไม่ถูกนำไปใช้) · ระหว่างรัน: สถานะ, 5 ขั้นตอน (`stage`), เปอร์เซ็นต์เฉพาะเมื่อ `progress` ไม่ใช่ null · เมื่อเสร็จ: จัดครบ X จาก Y, ครูชน/ห้องชน/กลุ่มชน, ผิดกฎอื่น, คะแนนโทษรวม, เวลาที่ใช้ (`stats` 9 ตัว), คำอธิบายว่าจัดวิชาไหนก่อน (`explanation`) · ตารางข้อขัดแย้ง (`conflicts[]`), รายการที่จัดไม่ได้พร้อมเหตุผล (`unscheduled[]`), เหตุผลที่จัดไม่ได้ทั้งชุด (`infeasibleReasons[]`), ข้อความเมื่อล้มเหลว/ยกเลิก |
| 4 ดูตาราง | เลือกมุมมองตามกลุ่ม/ครู/ห้อง และช่องค้นหา (ชื่อพร้อมรหัส) · ตารางรายสัปดาห์ คาบ 1–8 พร้อมเวลา แถวพักกลางวัน ช่อง "กิจกรรม" วันพุธคาบ 7–8 · แต่ละช่อง: ชื่อวิชา, ทฤษฎี/ปฏิบัติ, ห้อง, และครู (หรือกลุ่ม) · ช่องที่ซ้อนกันแสดงทุกวิชาพร้อมป้ายเตือน · จำนวนคาบรวมต่อสัปดาห์ |
| 5 ผลการใช้ AI | ตารางเทียบวิธีพื้นฐานกับวิธีของทีม (จุดที่ชน, ผิดกฎอื่น, คะแนนโทษ, เวลา) พร้อมป้าย "ดีกว่า" · กราฟแท่ง · คำอธิบายแต่ละวิธี (`description`: คืออะไร, ใช้ AI ตรงไหน, ตั้งค่าอะไร) · ป้าย "ข้อมูลจำลอง" (`isSimulated`) และข้อความว่ากดซ้ำด้วย seed เดิมแล้วได้ผลเหมือนเดิมหรือไม่ |
| 6 สรุปและส่งออก | ห้องแต่ละห้องถูกใช้กี่ % · ครูแต่ละคนสอนกี่คาบ · กลุ่มเรียนมีคาบว่างแทรกกี่คาบ · ผลคำขอพิเศษทีละข้อ (`requestResults[]`: ทำได้ครบ/ได้บางส่วน/ทำไม่ได้ พร้อม `reason`) · ปุ่มดาวน์โหลด PDF และ Excel |

ทุกหน้า: แถบเมนู 6 ขั้นตอน, ป้าย "ข้อมูลจำลอง" ถ้าอยู่โหมด mock, ข้อความผิดพลาดไทยพร้อมรหัสอ้างอิง (`requestId`)

**ที่มาของข้อมูล (ตามคำอธิบาย ยังไม่ตรวจซ้ำ):** มาจากเซิร์ฟเวอร์ = ข้อมูลนำเข้า, ปัญหาของไฟล์, การอ่านคำขอ, ผลจัดตาราง, ผลเปรียบเทียบ, ไฟล์ส่งออก · เว็บคำนวณเอง = ตารางรายสัปดาห์, จำนวนคาบรวม, % การใช้ห้อง, คาบต่อครู, คาบว่างของกลุ่ม (มี test: `timetable.test.js`)

**ข้อมูลส่วนบุคคล:** ชื่อครูที่แสดงในหน้า 2, 4, 6 คือชื่อที่อยู่ในไฟล์ที่ผู้ใช้อัปโหลด (ในไฟล์ตัวอย่างของฝั่งเรา เป็นชื่อสมมติที่สร้างเอง; ชื่อในไฟล์โจทย์จริงยังไม่ยืนยันว่าเป็นชื่อจริงหรือไม่ — ตรงกับ Q2 ใน SPEC §11) ขนาดกลุ่มใช้ตรวจความจุห้อง ไม่ได้แสดงบนหน้าจอ ไม่มีชื่อนักเรียน

**การเก็บสถานะ — แก้จากคำอธิบายเดิม:** คำอธิบายที่ฉันได้รับระบุว่า "เก็บในหน่วยความจำเท่านั้น ยังไม่ได้เก็บลง storage" ข้อนี้ **ล้าสมัยแล้ว** ตามที่ SPEC §8a ข้อ 5 ขอ ตอนนี้โค้ดบน working tree เก็บใน `sessionStorage` (ต่อแท็บ, หายเมื่อปิดแท็บ): `importId`, `jobId` ของงานที่จบแล้ว, seed, สถานะยืนยัน และ **รายการคำขอที่ยืนยัน (มีข้อความคำขอ ซึ่งอาจมีชื่อครู)** แล้วโหลดรายละเอียดกลับด้วย `GET /api/v1/imports/{id}` และ `GET /api/v1/schedules/{id}` ตอนเปิดหน้า/รีเฟรช ถ้า id หมดอายุ (404) หรือเซิร์ฟเวอร์ไม่ตอบ เว็บเริ่มจากสถานะว่าง ค่าที่อ่านกลับจาก storage ถูกตรวจด้วย zod ก่อนใช้ งานที่ยังไม่จบตอนรีเฟรชจะไม่ถูกติดตามต่อ (ข้อจำกัดที่รู้)

**สถานะการย้ายกลับ `/api/v1` (ตรวจแล้ว ณ เครื่องแพน):** ทำไปบน working tree **ยังไม่ commit ยังไม่ push** — คืน services/schemas/mocks/pages เป็นรูป `/api/v1` ฉบับ `7f1e46b`, เพิ่ม `infeasible` ใน `jobSchema` และ `JOB_TERMINAL_STATUSES`, ข้อความของ `QUEUE_FULL`/`JOB_ALREADY_RUNNING`/`infeasible`, ให้ `evaluationService.run` เริ่มงานแล้ว poll `GET /api/v1/evaluations/{id}` (ตามรูปแบบเสนอ pan-ai-004 R7 — **ยังรอคุณยืนยัน Q2**), และเก็บ `importId`/`jobId` ใน `sessionStorage` · lint ผ่าน, test 30 ตัวผ่าน (รวม 4 ตัวใหม่ของ `sessionStore`), build ผ่าน · **ยังไม่เคยเรียกเซิร์ฟเวอร์จริง** และยังไม่ได้เปิดดูใน browser หลังย้าย

## Proposals
- เมื่อคุณวาง response จริงของ F2 (C2 ใน pan-ai-004) ฉันจะตรวจกับ `apiSchemas.js` และรายงานเป็นข้อ ๆ — ฉันอ่านโค้ด F2 ที่ `api/backend@808a1e5` แล้วเห็นว่ารูป `importId/status/summary/issues/periods` + ข้อมูลทั้งชุดตรงกับ `importSchema` แต่ยังไม่ได้รันเทียบ

## Assumptions (ยังไม่ได้ตรวจ)
- ตารางหน้า 1–6 ด้านบนตรงกับโค้ดปัจจุบันทุกช่อง (ยังไม่ได้ตรวจซ้ำ)
- ฟิลด์ที่ระบุเป็น "ต้องมีจากเซิร์ฟเวอร์" ตรงกับที่ F3–F7 ของคุณจะส่งได้ครบ — ยังไม่เห็นโค้ด F3–F7

## Question / Response
- **Q1:** มีรายการแสดงผลข้างบนรายการไหนที่คุณคาดว่า Backend จะ **ส่งให้ไม่ได้ทัน** (เช่น `explanation`, `infeasibleReasons`, `requestResults[].reason`, `stats` ครบ 9 ตัว, `periods`/`requests` ใน `GET /imports/{id}`) เพื่อให้ฉันซ่อนหรือติดป้ายแทนที่จะให้เว็บปฏิเสธทั้งผล
- **Q2:** ถ้าคุณไม่ตอบ Q2 ของ pan-ai-004 ก่อน F6 ฉันจะคงรูปแบบ evaluations ตาม R7 — ยืนยัน/เสนอแบบอื่นได้ทุกเมื่อ

## Impact if unanswered
ถ้ามีฟิลด์ที่ Backend ส่งไม่ครบ เว็บจะปฏิเสธ response ทั้งก้อน (schema ตรวจเข้ม) กรรมการจะเห็นเป็นข้อผิดพลาดทั้งหน้าแทนที่จะเห็นหน้าที่แสดงบางส่วน
